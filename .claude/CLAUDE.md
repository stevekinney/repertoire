# Repertoire

A Claude Code plugin (`repertoire`) that also serves as its own marketplace. It lives at `github.com/stevekinney/repertoire`.

## Authoring skills, subagents, and workflows

Before writing or changing a skill, subagent, or workflow, read the guide for it. Each one links straight from here:

- [`documentation/authoring.md`](../documentation/authoring.md): what applies to all of them. Choosing the mechanism, descriptions, verification, safety, evals, and the pre-ship checklist.
- [`documentation/skills.md`](../documentation/skills.md): `SKILL.md` structure, procedure, references, and script contracts.
- [`documentation/subagents.md`](../documentation/subagents.md): when a separate worker is justified, tool scoping, output shape, and the delegation contract.
- [`documentation/workflows.md`](../documentation/workflows.md): when a script should hold the plan, orchestration shape, verification patterns, resume, and cost.

**Choose the mechanism first.** Use a skill for reusable method or knowledge, a subagent when separate execution materially helps, a workflow when many agents need orchestrating repeatably or their findings need cross-checking, `CLAUDE.md` for a short standing rule, and a hook, script, permission rule, or CI check for anything that must always hold. A one-off task needs no packaging.

Rules that always apply:

- Descriptions are written in the third person, say what the component does and when to use it (main use case first), name the near-misses it should not handle, and stay at or under 1,024 characters.
- Skills reference bundled files through `${CLAUDE_SKILL_DIR}`, and every shipped file is referenced from `SKILL.md` with a condition for loading it.
- Subagents declare an explicit `tools` allowlist and never set `hooks`, `mcpServers`, or `permissionMode`, which plugin subagents ignore.
- Workflows take their inputs through `args`, never call `Date.now()`, `Math.random()`, or an argless `new Date()`, and keep consequential actions such as pushing or deploying out of fan-outs.
- `bun run lint` must pass. It enforces the mechanical rules above for skills, subagents, and workflows; the guides cover the rest.

## Layout

- `.claude-plugin/plugin.json`: the plugin manifest. The version is set **only** here.
- `.claude-plugin/marketplace.json`: the marketplace manifest, with one entry pointing at `./`. Don't add a `version` to the entry, because it would have to be kept in sync with `plugin.json`.
- `src/skills/<skill-name>/`: **the source of truth for skills.** Edit here.
- `skills/`: **generated by `bun run build`. Never edit it by hand.** It's committed because installing a plugin copies the repo as it is, and nothing runs `npm install` or a build step.
- `agents/<agent-name>.md`: subagents, authored directly. Nothing transforms them, so there is no `src/agents/`.
- `workflows/<name>.js`: workflows, authored directly as plain JavaScript. Each runs as `/repertoire:<meta.name>`.
- `documentation/`: the authoring guides.
- `src/hooks/`: the source of the plugin's hook scripts, bundled by the build to `hooks/scripts/` (generated, committed). `hooks/hooks.json` is handwritten and registers them.
- `scripts/build.ts`: the build. `scripts/lint.ts`: the linter, with tests in `scripts/lint.test.ts`.

## How the build works

`bun run build` lints `src/skills/` and refuses to build if anything fails. Then it wipes `skills/` and regenerates it, and does the same for `hooks/scripts/` from the top-level files in `src/hooks/` (bundled the same way; `src/hooks/lib/` is library code). For skills:

- **Entry points:** `src/skills/<skill>/scripts/*.ts` (top level of `scripts/` only, excluding `*.test.ts`) are bundled with Bun into `skills/<skill>/scripts/<name>.mjs`. Each bundle targets Node, inlines every npm dependency, starts with `#!/usr/bin/env node`, and is executable.
- **Library code:** any other TypeScript file, such as `scripts/lib/*.ts` or `src/shared/*.ts`, is never emitted by itself. It ships only inside the bundles that import it.
- **Everything else** (`SKILL.md`, references, templates, dotfiles) is copied verbatim.

Rules that follow from this:

- In `SKILL.md`, refer to the **built** file through `${CLAUDE_SKILL_DIR}`: `node "${CLAUDE_SKILL_DIR}/scripts/<name>.mjs"`. Don't use `scripts/<name>.ts` or a bare relative path, because Claude's working directory is the user's project, not the skill folder. The linter maps `.mjs` references back to their `.ts` sources.
- Packages that skill scripts import go in `devDependencies`. They're only needed at build time.
- Scripts must run on Node. Importing `bun` or `bun:*` fails the build. `src/tsconfig.json` loads only Node types, so the `Bun.*` globals fail `bun run typecheck`. Packages with native addons can't be bundled.
- Don't add a shebang to the source. The build writes the Node shebang itself.

## How the linter works

`bun run lint` checks `src/skills/`, `agents/`, and `workflows/`. Every finding fails, and each one names the rubric checklist item it enforces (listed in `documentation/authoring.md`). It combines two sources:

- `@lostgradient/skillset`: `validateSkillMetadata` (with `target: 'claude'`), `validateSubagentMetadata`, and the workflow checks that mirror what Claude Code does when it loads a script (`parseClaudeWorkflowMeta`, `findClaudeWorkflowForbiddenApis`, `extractClaudeWorkflowCalls` with `claudeWorkflowAgentOptionsSchema`, and `checkClaudeWorkflowPhases`). Its warnings fail the lint too. A release can add or change rules, so the package is pinned to an exact version: upgrade it on purpose, then run `bun run test` and `bun run lint` and check what changed.
- Plugin rules in `scripts/lint.ts`. Skills set `name` explicitly, referenced paths exist, skill folders and files aren't symbolic links, script paths use `${CLAUDE_SKILL_DIR}`, and shipped files are referenced. Subagents have `tools`, no plugin-ignored fields, and descriptions that fit in 1,024 characters. Workflows have a kebab-case `meta.name` matching the filename, a third-person description of at most 1,024 characters, no keys in `meta` or `agent()` options that Claude Code ignores, and `repertoire:` references to subagents and workflows that exist, nested at most one level.

When adding a rule, add a test that proves it fires and a passing case that proves it doesn't fire on good input.

## Adding a skill

1. Decide it should be a skill (see `documentation/authoring.md`), then read `documentation/skills.md`.
2. Create `src/skills/<skill-name>/SKILL.md` with a kebab-case directory name and `name` and `description` frontmatter. `name` must match the directory name.
3. Put scripts in `src/skills/<skill-name>/scripts/` and other supporting files next to `SKILL.md`.
4. Run `bun run build`, then `/repertoire:optimize-component` on the new file.

## Adding a subagent

1. Complete the justification sentence in `documentation/subagents.md`. If it doesn't hold, write a skill instead.
2. Create `agents/<agent-name>.md` with `name`, `description`, and `tools` frontmatter, and the system prompt as the body.
3. Run `bun run lint`.

## Adding a workflow

1. Complete the justification sentence in `documentation/workflows.md`. If it doesn't hold, write a skill or subagent instead.
2. Load the bundled `/workflow-authoring` reference before writing the script.
3. Create `workflows/<name>.js`, starting with a pure-literal `export const meta = { name, description, phases }`.
4. Run `bun run lint`.
5. Run it on a small slice first, and read its `journal.jsonl` before trusting the result.

## Hooks

`hooks/hooks.json` registers one PreToolUse hook, `enforce-agent-limits`, from `src/hooks/enforce-agent-limits.ts` and its policy in `src/hooks/lib/agent-limits.ts`. It enforces what a subagent's `tools` allowlist can't: test-only writes for `repertoire:reenactor` and `repertoire:test-designer`, a read-only repository for the observer agents, and no push or publish for any plugin agent.

- It acts only on calls whose hook payload `agent_type` starts with `repertoire:`. The main session, other plugins' agents, and agents with bare names pass straight through.
- It is a guardrail, not a sandbox. It matches command and path text, so it can be routed around, and it **fails open**: a payload it can't parse is allowed, so a bug here can never lock a session out of its tools. Agent bodies still carry the instruction; the hook is the backstop.
- A new rule needs a test in `src/hooks/lib/agent-limits.test.ts` that proves it denies and a case that proves ordinary work still passes. A false denial breaks an agent mid-task, so prefer narrow rules.
- Hook scripts are Node-only and have no dependencies, like skill scripts.

## Optimizing a component

`/repertoire:optimize-component` audits components against `documentation/`, has a skeptic try to refute every finding, and rewrites the survivors in place. Run it after drafting or changing anything, with `args.paths` listing the files. It edits in place, so snapshot or commit first and read the diff afterwards. Rules it has to keep:

- No `agentType` anywhere in `workflows/optimize-component.js`. It is the plugin's own development tool and must run in a session where the plugin isn't installed, so `repertoire:*` agents can't be assumed to resolve.
- The audit runs on the session model; verify and rewrite default to Sonnet (`args.models` overrides). Checking quotes and applying small edits don't need the strongest model.
- The rewriter may edit existing files inside a skill's directory but never adds, deletes, or renames files. Findings that need a new file (usually "this checkable work wants a script") come back as `skipped` and are follow-up work.

## Pre-commit hook

Lefthook (`lefthook.yml`) runs four pre-commit jobs in order. Each runs only when its relevant files are staged, and the first failure stops the hook:

1. **typecheck:** `bun run typecheck`, when `src/`, `scripts/`, `tsconfig.json`, `package.json`, or `bun.lock` changes.
2. **test:** `bun run test`, when `scripts/`, `package.json`, or `bun.lock` changes.
3. **lint:** `bun run lint`, when `src/`, `agents/`, `workflows/`, `scripts/`, `package.json`, or `bun.lock` changes.
4. **build skills:** `bun run build && git add skills`, when `src/`, `skills/`, `scripts/`, `package.json`, or `bun.lock` changes. This keeps the committed bundles in step with the committed source.

- Lefthook sets unstaged changes aside while the hook runs. A partially staged commit therefore bundles only what's staged.
- A type error, a failing test, a lint finding, or a failing build blocks the commit.
- Hand edits to `skills/` are overwritten.
- `bun install` installs the hook. If it's missing, run `bunx lefthook install`. To skip it once, run `LEFTHOOK=0 git commit ...`. CI still catches the problems it would have.

## CI

`.github/workflows/ci.yml` runs on pushes to `main` and on pull requests. It runs `bun install --frozen-lockfile`, then `typecheck`, `test`, `lint`, `check`, and `validate`. It installs the latest Claude Code for validation, so a new strict-mode rule can fail CI without any change to this repo.

## Verifying changes

- `bun run build` regenerates `skills/`. The pre-commit hook does this for you.
- `bun run check` fails if `skills/` is out of date with `src/skills/`, or if `src/skills/` fails the lint.
- `bun run lint` checks skills, subagents, and workflows.
- `bun run test` runs the linter's tests.
- `bun run typecheck` type-checks `scripts/` and `src/**/*.test.ts` against Bun types, and the rest of `src/` against Node types.
- `bun run validate` runs `claude plugin validate --strict` on both manifests and the built skills. It must pass with no warnings.
- The Bun version is pinned in `package.json` (`packageManager`), because bundle bytes depend on it and `check` compares bytes.
- `claude --plugin-dir .` loads the working copy for a manual test.
- `claude plugin details repertoire` shows the component inventory and the projected token cost.

## Releasing

Bump `version` in `.claude-plugin/plugin.json`, then run `claude plugin tag .` to create the `repertoire--v<version>` tag.
